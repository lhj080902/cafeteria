# Cafeteria 인수인계 (2026-11-25 기준)

Claude Code 클라우드 세션에서 만든 작업을 로컬(Claude Code CLI)로 넘기기 위한 문서다.
코드 규칙과 명령어는 저장소 루트의 `CLAUDE.md`, 사용자용 설명은 `README.md` 에 있다. 여기에는 **지금 상태, 남은 일, 왜 이렇게 만들었는지**만 적는다.

## 1. 지금 상태

- 저장소: https://github.com/lhj080902/cafeteria (`main`, 공개)
- 릴리스된 최신 버전: **1.4.0** (모드와 런처가 같은 번호를 쓴다)
- 릴리스: [v1.4.0](https://github.com/lhj080902/cafeteria/releases/tag/v1.4.0) – `Cafeteria-Setup-1.4.0.exe`, `.blockmap`, `latest.yml` 세 파일이 올라가 있다. 릴리스에서 받은 `latest.yml` 이 빌드 결과와 같고, 그 해시·크기가 설치 파일과 일치하며, 올라간 세 파일의 sha256 이 빌드 결과와 같은 것을 확인했다. ([v1.3.0](https://github.com/lhj080902/cafeteria/releases/tag/v1.3.0) 도 같은 확인을 했다)
- **1.3.0 은 2026-11-24 에 릴리스했다.** 런처 안 Microsoft 로그인과 게임 바로 실행을 넣었고, 모드 코드는 바뀌지 않았다(번호만 맞춤). 같은 날 실제 Windows PC 에서 로그인, 게임 실행, 1.2.2 설치본의 자동 업데이트를 확인했다(3번 표). 태그 `v1.3.0` 은 `main` 의 `6021fde` 이고, 설치 파일은 그 바로 앞 커밋 `9d5f98f` 에서 빌드했다. 두 커밋의 차이는 게임 테스트 소스(`src/gametest`) 한 줄뿐이고 배포용 jar 와 런처에는 들어가지 않는다.
- **1.4.0 은 2026-11-25 에 릴리스했다.** 모드에 두 가지가 들어갔다. HUD 편집 개선(꼭짓점을 끌어 1% 단위로 크기 조절, 타이틀·스코어보드·보스바 위치·크기, 채팅 배율)과 안개 제거(`no_fog`: 거리 안개, 물속, 용암 속). 런처 코드는 바뀌지 않았다(번호만 맞춤). 게임 테스트는 GitHub Actions 에서 통과했고, HUD 편집 쪽은 Windows 개발 PC 에서도 통과했다. **안개 제거는 Windows 에서 돌린 적이 없다** (3번 표). 사용자가 실제로 플레이하며 새 기능을 써 본 적은 아직 없다. 사용자가 안개 제거까지 넣어 1.4.0 으로 한 번에 릴리스하기로 정했다. 태그 `v1.4.0` 은 `main` 의 `04ad109` 이고, 설치 파일도 그 커밋에서 빌드했다 (GitHub Actions 네 작업이 그 커밋에서 통과한 뒤에 올렸다). **설치해 둔 1.3.0 이 1.4.0 으로 자동 업데이트되는 것은 확인하지 못했다.**
- 대상: Minecraft 1.21.4, Fabric Loader 0.20.1, Fabric API 0.119.4+1.21.4, Windows. (버전은 `mod/gradle.properties` 와 `launcher/src/main/constants.js` 에서 맞춘다)

### 사용자가 처음에 정한 것

- 루나 클라이언트처럼 PvP 기능만 기본으로 넣고, 나머지는 사용자가 모드를 직접 추가한다.
- 런처 이름은 **카페테리아(Cafeteria)**. Minecraft **1.21.4 하나만**, Fabric, Windows.
- 로그인과 게임 실행은 처음에는 **공식 Minecraft 런처에 맡기기로** 했다 (런처는 Fabric 프로필과 모드를 설치하고 공식 런처를 열었다). **2026-11-24 에 바뀌었다**: 사용자가 런처 하나로 로그인하고 바로 게임에 들어가게 해 달라고 요청해서 1.3.0 에서 Microsoft 로그인과 바로 실행을 넣었다. 공식 런처 방식은 설정의 "게임 실행 방식"에서 고를 수 있게 남겼다. 풀어낸 방법은 4번 참고.
- CurseForge API 키는 런처에 넣지 않고 사용자가 설정에 직접 입력한다.
- 결과물은 설치 파일(Setup.exe)로 받는다.

## 2. 들어 있는 기능

### 모드 (`mod/`)

| 묶음 | 모듈 id (기본 상태) |
| --- | --- |
| 기능 | `freelook`(켜짐), `zoom`(켜짐), `hitbox`(켜짐), `fullbright`(꺼짐), `low_fire`(꺼짐), `no_fog`(꺼짐), `no_tutorial`(켜짐), `menu_background`(켜짐), `chat_time`(켜짐), `infinite_chat`(켜짐), `screenshot`(켜짐) |

기본 키: 모드 설정 = 오른쪽 Shift, 프리룩 = 왼쪽 Alt, 줌 = C, 풀브라이트 = G.

코드 길잡이 (`mod/src/main/java/io/github/lhj080902/cafeteria/`):

## 3. 검증한 것과 못 한 것

1.2.2 까지의 검증은 모두 **Linux 컨테이너**에서 했다. 1.3.0 작업 중에 Windows 에서 단위 테스트와 짧은 부팅 검사를 처음 돌렸다 (아래 표).

1.4.0 부터 모드 게임 테스트는 **GitHub Actions** 가 돌린다 (`.github/workflows/gametest.yml`). `mod/` 가 바뀐 push 마다 개발 환경, 배포용 jar, 배포용 jar + Xaero's Minimap·World Map, 배포용 jar + Sodium 0.6.13 네 가지를 따로 실행하고, 스크린샷과 로그를 실행 결과에 붙인다 (`gh run download <번호>`). 함께 돌리는 모드는 Modrinth 에서 받아 고정한 sha512 로 확인하고, 실행이 끝나면 로그의 모드 목록에서 그 모드가 실제로 올라갔는지 확인한다. 개발 PC 에서는 게임 테스트가 게임 창을 띄워서 사용자가 게임을 하는 동안 돌릴 수 없기 때문에 넣었다. Linux 에서 도는 것이라 Windows 전용 동작은 확인되지 않는다.

## 4. 남은 일

### 사용자의 결정을 기다리는 것

1. **Microsoft 로그인 + 게임 직접 실행**: 구현됨. 아래 "1.3.0 에서 해결한 것" 참고.
2. **포션 HUD 의 "기본 아이콘 숨김" 기본값**: 지금은 꺼짐. 켜짐으로 바꿀지 물어봤고 답을 받지 못했다.
3. **릴리스 자동화 (GitHub Actions)**: 태그를 올리면 빌드해서 릴리스를 만드는 워크플로를 제안했고 답을 받지 못했다.

### 1.3.0 에서 해결한 것: Microsoft 로그인 + 게임 직접 실행

- 예전에 걸림돌로 본 것은 Azure 앱 등록과 Minecraft API 사용 허가였다. 이번에는 **마인크래프트 공식 런처의 공개 클라이언트 ID**(`00000000402b5328`)로 로그인 창을 열어서 그 둘이 필요 없다. 참고한 다른 런처(`msmc` 라이브러리)가 같은 방식을 쓰고, 실제 PC 에서 확인된 방식이다.
- **위험**: 이것은 Microsoft 의 승인을 받은 방식이 아니라 **비공식 방식**이다. Microsoft 가 이 클라이언트 ID 를 막으면 모든 사용자의 로그인이 안 된다. 그래서 공식 런처 방식을 설정에서 고를 수 있게 남겨 뒀다 (대비책).
- 절차: 로그인 창에서 Microsoft 승인 코드, 토큰, Xbox Live, XSTS, Minecraft 토큰, 프로필 순서. refresh 토큰은 `userData/account.json` 에 암호화(`safeStorage`)해 두고 필요할 때 갱신한다. 모두 런처 안에 직접 구현했다 (5번 참고).
- 사용자가 정한 것은 그대로다: 비정품(오프라인) 로그인과 토큰 붙여 넣기 로그인은 넣지 않았다. 여러 계정 전환, 스킨 표시, 1.21.4 외 버전, Windows x64 가 아닌 곳에서의 바로 실행(그런 곳은 공식 런처 방식으로만 동작)도 하지 않았다.
- 만들어진 것: 게임 파일 받기(약 630MB, 처음 한 번), Java 21 받기, 실행 인수 조립, 홈의 계정 줄과 "실행 중" 표시, 설정의 "게임 실행 방식"(`launchMode`: `direct` 기본 / `official`).

### 이 저장소 밖의 일: FastPack

- FastPack 은 사용자의 다른 저장소 `lhj080902/jamsuham` 의 `tools/fastpack-mod` 에 있는 모드다 (서버 리소스팩을 재접속 때 다시 적용하지 않게 함).
- 0.3.0 의 문제 두 개를 찾아 0.3.1 로 고쳤다. 고친 jar 와 패치 파일(`fastpack-0.3.1.patch`)을 사용자에게 전달했고, **jamsuham 저장소에는 아직 반영하지 않았다.**
  1. 연결이 맺어지기 전에 `connection.getRemoteAddress()` 를 읽어 null 이 나오면 같은 서버를 "다른 서버"로 판정해 팩을 다시 받았다 → 접속 화면에서 누른 주소(`host:port`)를 서버 키로 쓰도록 수정.
  2. 싱글플레이 월드에 들어갈 때 남겨 둔 서버 팩이 그대로 적용됐다 → 월드 로드 전에 정리하도록 수정. (`doWorldLoad` 안에서 리소스를 다시 읽으면 멈추므로, 로드를 취소하고 정리가 끝난 뒤에 다시 호출한다)
- 이런 모드의 호환성은 `mod/tools/pack_server.py` 와 `ServerResourcePackTest` 로 확인한다 (README 의 개발 항목 참고).

## 5. 알아 두면 좋은 결정과 함정

- **줌과 손**: 줌은 월드를 그리는 시야각만 바꾼다(`GameRendererMixin` 이 `renderLevel` 안의 `getFov` 호출 결과만 수정). 손은 확대되지 않는다. 사용자가 "줌하면 팔도 같이 줌된다"고 한 것은 손이 커진다는 뜻이 아니라 **줌한 화면에 손이 남아 시야를 가린다**는 뜻이었다. 그래서 줌하는 동안 손을 화면 아래로 내리는 것을 기본으로 했다(`zoom_hand_hidden`).
- **메뉴 배경**: 바닐라는 메뉴 배경을 25% 만 어둡게 하고 흐림 효과를 건다. 사용자 환경에서 ESC 메뉴 배경이 까맣게 나왔는데, 원인은 재현하지 못했다(흐림 효과가 깨지는 것으로 추정). `menu_background` 모듈이 흐림을 건너뛰고 어둡기를 직접 정한다.
- **HUD 는 채팅보다 앞에** 그린다 (`IdentifiedLayer.CHAT` 뒤에 레이어를 붙임). 사용자 요청이다.
- **스크린샷 복사**: 게임이 `java.awt.headless=true` 로 켜 두는 것을 모드 초기화 때 false 로 바꿔서 AWT 클립보드를 쓴다. macOS 는 지원하지 않는다.
- **설정 id 를 일부러 바꾼 적이 있다**: `zoom_hide_hand`(기본 꺼짐) → `zoom_hand_hidden`(기본 켜짐). 이미 저장된 "꺼짐"이 남지 않게 하려는 것이었다.
- **모드 업데이트는 자동으로 바꾸지 않는다.** 확인만 자동이고 교체는 버튼을 누를 때만 한다. 새 파일을 받아 해시를 검증한 뒤에 예전 파일을 지운다.
- **같은 모드 id 의 jar 를 추가하면 예전 파일을 지운다.** 사이트에 없는 모드(FastPack 등)의 업데이트 방법이다. Cafeteria 모드 자체는 런처가 관리하므로 따로 넣지 못하게 막았다.
- **설치 파일은 Wine 없이 만든다.** `launcher/scripts/build-win.js` 가 electron-builder 안의 `UninstallerReader` 를 쓰도록 바꾸고, 빌드 뒤에 NSIS 무결성 검사를 직접 해 본다.
- **서명되지 않은 실행 파일**이라 Windows 가 처음 실행할 때 경고를 띄운다.
- **로그인과 게임 실행은 라이브러리(`msmc`, `minecraft-launcher-core`) 대신 직접 구현했다.** `minecraft-launcher-core` 는 호스트 허용 목록도 해시 검증도 없이 받아서 CLAUDE.md 의 런처 보안 규칙을 지킬 수 없다. `msmc` 는 `http.js`(시스템 프록시, 테스트용 가짜 fetch)를 거치지 않고 의존성을 끌어오는데, 로그인 절차 자체는 요청 6개뿐이라 직접 만들었다. 새 npm 의존성은 없다. 다운로드는 기존 `http.download`(허용 목록, sha1, `.part`)를 그대로 쓴다.
- **고정 해시 사슬과 Fabric 구성 고정**: `constants.js` 에 `1.21.4.json` 과 Java 런타임 목록의 주소와 sha1 을 고정하고, 거기서 `client.jar`, 라이브러리, 에셋 인덱스, 에셋, Java 파일의 sha1 이 이어진다. 바로 실행에서는 `meta.fabricmc.net` 의 Fabric 프로필 JSON 을 **받지 않는다** (고정할 해시가 없어 사슬이 끊긴다). 대신 `mainClass`, JVM 인수, 라이브러리 8개의 이름과 sha1 을 `constants.js` 의 `FABRIC` 에 고정했고, 실제 서버 검사가 그 값이 Fabric 서버의 지금 내용과 같은지 비교한다. 공식 런처 방식은 지금처럼 프로필 JSON 을 받아 `.minecraft` 에 저장한다. Minecraft, Fabric, Java 버전을 올릴 때는 이 상수를 같이 바꿔야 한다.
- **게임 파일 위치**: 런처 데이터 폴더 `%APPDATA%\.cafeteria` 고정 (`paths.js` 의 `dataDir()`, 테스트용 `CAFETERIA_DATA_DIR`). 게임 폴더 설정을 바꿔도 게임 파일은 여기 남는다. Java 는 `runtime/<component>-<version>` 폴더(예: `java-runtime-delta-21.0.7`)에 두고 파일 목록은 `runtime/<component>-<version>.json` 에 둔다. 버전이 폴더 이름에 들어 있어서 Java 를 올려도 예전 파일과 섞이지 않는다.
- **`javaw.exe` 를 쓴다** (`java.exe` 아님). `java.exe` 는 콘솔 창이 뜨는데, 그 창을 숨기려고 `windowsHide` 를 켜면 게임 창까지 숨겨질 위험이 있다. 참고한 다른 런처에서 실제로 확인된 조합이 `javaw.exe` 에 `windowsHide` 를 켜지 않는 것이라 따랐다. 2026-11-24 실제 실행에서 게임 창이 정상으로 떴다. 한계: JVM 이 아예 못 뜨면 `javaw.exe` 가 오류 창을 띄우고, 그 창을 닫을 때까지 런처는 "실행 중"으로 본다. 게임을 켜 둔 채 런처를 껐다 켜면, 새로 켠 런처는 그 게임을 모른다. `ALREADY_RUNNING` 검사는 그 런처가 직접 띄운 게임만 보므로 플레이를 막지 않고 보통의 플레이 절차를 그대로 밟는다. 이때 실행 중인 게임이 모드 jar 를 열어 두고 있어서 모드 복사 단계(`installer.js` 의 `installMods`)가 실패할 수 있다. 실제로 어떻게 되는지는 **확인하지 못했다**.
- **목록 파일(`1.21.4.json`, 에셋 인덱스, Java 목록)은 매번 디스크 내용의 sha1 을 확인**하고 맞을 때만 쓴다. 일반 게임 파일은 평소에는 크기만 보고, 받을 때는 항상 해시를 검증한 뒤 임시 파일에서 이름을 바꾼다. 설치 복구는 전체 sha1 을 다시 계산한다. 공식 런처의 `.minecraft` 에 같은 파일이 있고 sha1 이 맞으면 복사해서 다시 받지 않는다 (Java 는 대상이 아님).
- **자동 업데이트에 "게임 중 설치 금지"를 넣지 않았다.** 참고한 다른 런처에는 있지만, NSIS 설치 프로그램은 설치 폴더 안의 프로세스만 끝내고 게임은 `%APPDATA%\.cafeteria` 의 Java 로 돌기 때문에 업데이트가 게임을 죽이지 않는다. 또 넣으면 "플레이 후 런처 닫기"를 켠 사용자는 런처가 늘 게임 중에 꺼져서 업데이트가 영영 설치되지 않는다. 업데이트 코드는 이번에 바꾸지 않았다.
- **Windows 에서 처음 드러난 테스트 2건** (1.3.0 작업을 시작할 때 Windows 의 `npm test` 기준선이 106개 중 2 실패였다. 커밋 `dcf3716`): (1) `importer.test.js` 가 구분자가 다른 경로를 그대로 비교했다. 양쪽을 `path.normalize` 로 맞췄다. (2) `mod-installer.js` 가 `a:b.jar` 같은 이름을 Windows 에서 거부하지 못했다. Windows 의 `path.basename` 이 콜론까지를 잘라 `b.jar` 로 만들기 때문이다. `path.basename` 을 부르기 전에 `:` 가 든 원래 이름을 거부하도록 고쳤다.
- **클라우드 세션의 제약**(로컬 CLI 에는 없음): 릴리스를 만들 수 없었고, 사용자가 요청하지 않은 외부 모드(Sodium·Iris)를 받아 실행하는 것은 권한 단계에서 거부됐다.

### 1.4.0 의 바닐라 HUD 조절 (타이틀, 스코어보드, 보스바, 채팅)

- 바닐라가 그리는 것을 다시 그리지 않는다. 그리기 메서드(`Gui.renderTitle`, `Gui.displayScoreboardSidebar`, `BossHealthOverlay.render`)를 `@WrapMethod`(`require = 0`)로 감싸 이동·배율 변환만 걸고, 예외로 끝나도 변환을 되돌린다. 옮기지 않았고 100%면 변환을 걸지 않아서 화면이 바닐라와 같다.
- 바닐라가 그릴 상자는 모드가 같은 계산으로 따로 구한다 (`TitleHud.box`, `ScoreboardHud.box`, `BossbarHud.box`). **Minecraft 버전을 올릴 때 바닐라의 배치 숫자가 바뀌었는지 확인해야 한다.** 숫자가 어긋나면 편집 화면의 테두리와 옮긴 자리가 실제 그림과 어긋난다 (게임 테스트가 픽셀로 잡는다). 타이틀 상자는 접근성 설정의 "글자 배경"이 "모든 곳"이면 바닐라가 글자 뒤에 까는 배경(글자 둘레로 2, 타이틀은 4배라 화면에서 8픽셀)까지 넣는다.
- 상자는 필요할 때만 구한다. 믹스인은 상자를 구하는 식만 넘기고(`VanillaHudElement.begin`), 옮기지 않았고 100%면 편집 화면처럼 상자를 묻는 쪽이 있을 때만 계산한다. 스코어보드 상자는 점수 목록을 걸러서 정렬해야 나오므로, 매 프레임 구하면 바닐라가 하는 일을 한 번 더 하게 된다. 옮겼거나 크기를 바꾼 요소는 변환에 상자가 필요해서 프레임마다 한 번 구한다 (바닐라 계산과 합쳐 두 번. 사용자가 손댄 경우에만 드는 비용이다).
- 옮기기 전에는 바닐라 자리를 따른다 (`VanillaHudElement` 의 `moved` 가 false). 크기만 바꾸면 바닐라 상자가 여유 공간에서 차지하던 비율을 유지해서 가운데·오른쪽 끝 정렬이 남는다. 한 번 옮기면(`setPosition`) 다른 HUD 처럼 비율로 기억하고, 설정 파일에 `"moved": true` 로 남는다. 꼭짓점을 끌어도 옮긴 것으로 친다. 옮기지 않았고 100%면 요소의 자리는 바닐라 상자 그대로다 (화면보다 넓어서 양쪽으로 넘친 타이틀도 그 자리를 가리킨다). 크기를 바꾼 뒤에도 화면보다 크면 왼쪽·위에 붙인다.
- "화면에 떠 있는지"는 `HudRenderer.frame()` 으로 가린다. 바닐라의 스코어보드·타이틀·보스바는 같은 프레임에서 우리 HUD 레이어(채팅 뒤)보다 먼저 그려진다. 떠 있지 않으면 편집 화면에서만 예시를 그린다.
- 채팅 배율은 `ChatComponent.getScale()` 과 `getWidth()` 의 반환값에 곱한다 (`@ModifyReturnValue`). 그리기·줄바꿈·마우스 좌표 변환이 모두 이 두 값을 거쳐서 한 줄의 글자 수와 클릭 위치가 유지된다. 채팅은 옮기지 않는다 (사용자가 "배율만"으로 정함).
- 다만 "폭 ÷ 글자 배율"을 계산하는 네 곳(`render`, `addMessageToDisplayQueue`, `getMessageLineIndexAt`, `handleChatQueueClicked`)은 `@ModifyArg`(`require = 0`)로 배율을 곱하기 전의 두 값을 쓴다. 배율을 곱한 폭은 정수로 내림되므로 그 값을 다시 나누면 1~2픽셀 좁아지기 때문이다 (기본 설정에서 151개 배율 중 120개가 그랬다). 네 곳 모두 그 메서드에서 `Mth.floor(double)`(`render` 는 `Mth.ceil(float)`)을 처음 부르는 자리다. **Minecraft 버전을 올릴 때 이 순서가 그대로인지 확인해야 한다.** 주입에 실패하면 줄바꿈 폭이 1~2픽셀 좁아질 뿐 게임은 켜진다 (`testChatScale` 의 4-1 단계가 잡는다).
- 크기 설정 id 는 그대로 `scale` 이고 단위만 0.1 에서 0.01 로 줄였다. 저장된 값은 그대로 읽힌다.

### 1.4.0 의 안개 제거 (`no_fog`)

- 사용자가 요청한 것: 켜고 끌 수 있는 안개 제거, 그리고 물·용암에 들어갔을 때 맑게 보이는 것. 스위치 셋(거리 / 물속 / 용암 속, 기본 모두 켜짐)과 "기본 꺼짐", "단축키 없이 설정 화면에서만"은 설계를 보여 주고 승인받았다.
- `FogRenderer.setupFog` 의 반환값을 `@ModifyReturnValue`(`require = 0`)로 바꾼다. 지형용 안개(`FOG_TERRAIN`)일 때만 시작·끝 거리를 아주 멀리(`NoFogModule.FAR_START`, `FAR_END`) 보내고 색과 모양은 그대로 둔다. 끝 거리를 0(`FogParameters.NO_FOG`)으로 두지 않는 이유: Sodium 은 "렌더 거리와 안개 끝 거리 중 작은 쪽"까지만 청크를 찾아서, 끝이 0이면 지형이 사라진다.
- 건드리지 않는 것: 하늘용 안개(`FOG_SKY`. 그래서 물속에서 위를 보면 물색이고 용암 속 배경은 주황색 그대로다), 실명·어둠 효과가 걸린 동안의 안개(용암·물속에서도), 가루눈 속, 다른 모드가 추가한 안개 종류.
- 물속에서는 화면 전체에 덮이는 물 무늬(`ScreenEffectRenderer.renderWater`)도 그리지 않는다 (`require = 0`). 이것만으로도 벽 색이 파란 쪽으로 10쯤 밀려서, 게임 테스트가 공기 중 색과 똑같은지로 잡는다. 실명·어둠 중에도 무늬는 숨긴다 (안개만 남긴다).
- 물속·용암 속 스위치만 켜고 거리 스위치를 꺼도, 액체 안에 있는 동안에는 거리 안개가 없다 (두 거리를 한꺼번에 멀리 보내기 때문).
- 용암 속에서 화면을 가리는 불꽃은 이 기능이 아니라 `낮은 화염`이 내린다.
- **Sodium 과 함께일 때의 한계**: Sodium 0.6.13 은 카메라가 움직일 때만 "그릴 청크 목록"을 다시 만든다. 액체 속에 가만히 선 채로 안개 제거를 켜면 안개 밖에 있던 청크는 마우스를 움직여야 나타난다. 미리 켜 둔 채로 들어가면 처음부터 보인다. Sodium 쪽 동작이라 모드에서 손대지 않았고(README 에 적어 둠), 게임 테스트는 켠 뒤 카메라를 1픽셀 움직인다 (`nudgeCamera`).
- 게임 테스트 `testNoFog`: 20칸 위에 바다 랜턴으로 폭 1칸 통로를 만들고 끝에 라임색 콘크리트를 세워 화면 한가운데 색을 잰다. 바다 랜턴이라 공기·물·용암 어디서나 벽이 같은 밝기다. 검사하는 동안 입자는 "최소", 낮은 화염은 100%로 둔다 (불꽃과 입자가 재는 자리를 덮는다).
- 서버에 따라 금지하는 기능일 수 있다. 그래서 기본은 꺼짐이고 README 의 "서버 규칙" 안내에 넣었다.
